МАКСИМ — BACKEND, ЛОГИКА ПЛАНИРОВАНИЯ И ИНТЕГРАЦИЯ

Твоя цель: надёжный сервер, который строит план, пересчитывает его без выбранной
машины и возвращает проверяемое сравнение. Ты также интегратор основной ветки.
Сначала прочитай 00_Общий_план.txt: там границы, контракт, Git и общий тайминг.
Ниже — подготовительный сценарий; после получения кейса скорректировать задачи.

1. ТВОЯ ОБЛАСТЬ
backend/app/main.py, domain.py, routing.py, schemas.py, models.py,
repository.py, imports.py, database.py, backend/pyproject.toml.
backend/tests/*, кроме test_agent*.py. Общий контракт — docs/team/00_Общий_план.txt.
Не редактируешь frontend, backend/app/agent и документацию демо.
Ветка: dev_Max.

2. СТЕК И ПОДГОТОВКА
Python >=3.14; FastAPI; Pydantic; SQLAlchemy; SQLite; pytest/httpx.
Сначала использовать уже существующие библиотеки и структуры.
В PowerShell из корня проекта:
  cd backend
  python --version
  python -m venv .venv
  .\.venv\Scripts\python.exe -m pip install -e ".[dev]"
  .\.venv\Scripts\python.exe -m pytest -q
  .\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
Проверить, что python действительно нужной версии; при необходимости выбрать
установленный Python 3.14 через py -3.14.
Документация запущенного API: http://127.0.0.1:8000/docs.
Для тестов использовать временную SQLite, не пользовательскую БД.
Прочитать routing.py, repository.py, main.py, schemas.py и test_api.py.

5. ЭТАП В — СМЫСЛ РАСЧЁТА И ПРОВЕРКИ
Текущий алгоритм назначает заказ первой подходящей машине по ID, затем выбирает
ближайшие остановки. Это исходный baseline; он не гарантирует минимум пути.
[ ] Вместимость ни одной машины не превышена.
[ ] Каждый заказ встречается ровно один раз: в маршруте или среди неназначенных.
[ ] Исключённая машина не получает остановки.
[ ] Если недоступны все машины, все заказы получают явную причину неназначения.
[ ] Повторение одинакового запроса даёт тот же состав маршрутов и метрики.
[ ] Исходный сохранённый план не изменился после перепланирования.
[ ] Проверены неизвестный ID, устаревший план, пустой список исключений.
[ ] Сравнение корректно при нулевых значениях и отрицательных delta.
[ ] Решён смысл order.status: завершённые/отменённые не включать в расчёт,
    если такие статусы допускаются выбранным кейсом; согласовать набор статусов.
[ ] Уточнён ETA: сейчас код прибавляет обслуживание текущей точки до записи ETA.
    Выбрать явную семантику: прибытие или завершение обслуживания; сообщить UI.
Добавлять тесты именно на бизнес-ограничения и ошибки, а не копии реализации.

7. P1 — ТОЛЬКО ПОСЛЕ ОБЩЕГО P0
Если кейс требует улучшения маршрутов, добавить выбор машины по дополнительному
расстоянию при соблюдении вместимости. Сравнить с исходным алгоритмом на одном
наборе заказов. Показывать качество обслуживания вместе с километражем.
Реальные дороги/сложный solver подключать только при требовании кейса и наличии
времени на интеграцию; выбор технологии принять отдельно.

8. ЧТО ПЕРЕДАТЬ КОМАНДЕ
Константину: форматы ответов, коды ошибок, семантику ETA, работающий endpoint.
Нетесову: точку подключения router, формат контекста, ограничения сценария.
В PR: что работает, как проверить, какие тесты прошли, что осталось.
Сливать небольшими порциями: контракт → endpoint → проверки → AI-подключение.
После каждого интеграционного слияния проверять затронутые тесты; перед сдачей
выполнить весь backend pytest и вместе с Константином проверки frontend.
