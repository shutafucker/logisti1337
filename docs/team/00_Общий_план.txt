1. ЦЕЛЬ И ГРАНИЦЫ
Подготовить основу, которую можно адаптировать к реальному заданию по логистике.
Конкретного задания пока нет. Всё ниже — внутренний план, а не требования жюри.
Тренировочный сценарий: диспетчер загружает заказы и машины, получает план,
сообщает о недоступной машине, сравнивает исходный и новый планы.
AI преобразует сообщение в проверяемое действие и объясняет результат.
Расстояния, вместимость, назначения и метрики рассчитывает программный код.

Если кейс про склад или документы, маршрутизация не становится обязательной:
сохраняем подходящие части проекта и меняем предметную логику.

4. РАБОТА В ОДНОМ РЕПОЗИТОРИИ
Каждый работает в отдельном клоне на своём компьютере.
Не переключать ветки в одной общей физической папке параллельно.
Основная ветка — фактическая основная ветка репозитория; ниже обозначена BASE.
Определить её перед стартом, не предполагать автоматически main или master.

Ветки:
Максим: feature/maxim-backend
Константин: feature/konstantin-ui
Нетесов: feature/netesov-agent-demo

Порядок:
1) git status — убедиться, что свои изменения сохранены.
2) git fetch origin
3) git switch BASE
4) git pull --ff-only origin BASE
5) git switch -c feature/ИМЯ-ЗАДАЧА — один раз при создании ветки.
6) Делать небольшие коммиты, добавлять конкретные файлы через git add <путь>.
7) git push -u origin feature/ИМЯ-ЗАДАЧА
8) Создать PR с результатом, проверками и изменениями контракта.
9) Максим проверяет и сливает; автор помогает разрешить конфликты своей области.
10) После слияния: git fetch origin, затем git merge origin/BASE в рабочей ветке.
BASE и ИМЯ-ЗАДАЧА — обозначения, их нужно заменить реальными именами.
Не использовать force push в общую ветку. Не коммитить ключи, .venv, node_modules, БД.
Если правила сдачи задают другую схему Git, следуем им.

Владение файлами:
Максим — backend/app/*, кроме нового backend/app/agent/*;
          backend/pyproject.toml, backend/tests/*, кроме test_agent*.py;
          общий API-контракт в этом файле после первичного согласования.
Константин — весь frontend/, включая зависимости и lock-файл.
Нетесов — backend/app/agent/*, backend/tests/test_agent*.py,

5. ОБЩИЙ КОНТРАКТ ДЛЯ ТРЕНИРОВОЧНОГО СЦЕНАРИЯ
Это предлагаемые новые интерфейсы. Сейчас в проекте их нет.
За первые 30 минут подготовки Максим подтверждает контракт, Константин делает
по нему UI, Нетесов — AI-модуль. Обновлять контракт до изменения реализации.
Существующие /imports/orders, /imports/vehicles, /route-plans, /dashboard сохранить.

POST /replans
Запрос: {"base_plan_id":1,"unavailable_vehicle_ids":["VAN-02"]}
Для P0 поддержать исключение машин без других действий и временных окон.
Ответ:
{
  "base_plan_id":1,
  "plan":{...существующий RoutePlanResponse...},
  "comparison":{
    "before":{"assigned_orders":8,"unassigned_orders":2,
      "distance_km":24.5,"duration_minutes":130},
    "after":{"assigned_orders":7,"unassigned_orders":3,
      "distance_km":21.0,"duration_minutes":115},
    "delta":{"assigned_orders":-1,"unassigned_orders":1,
      "distance_km":-3.5,"duration_minutes":-15}
  },
  "unavailable_vehicle_ids":["VAN-02"]
}
Числа выше — пример формата, не обещание результата.
delta всегда after минус before. Меньше километров при меньшем числе доставок
нельзя автоматически называть улучшением.
Длительность — сумма длительностей маршрутов, не время окончания всей доставки.
P0: сценарный расчёт на текущих заказах с последним актуальным исходным планом.
Исходный план сохраняется неизменным; статусы машин в БД не меняются.
Максим возвращает сравнение в одном ответе; UI хранит его до следующего импорта.
Проверки: неизвестные ID → 404; несовместимый/устаревший план → 409;
ошибка формата → 422. Ошибка: {"detail":"понятное сообщение"}.
Не представлять расчёт как работу с уже доставленными заказами: учёта исполнения
маршрута пока нет. После изменения импортных данных выбрать новый базовый план.

POST /agent/interpret
Запрос: {"message":"Машина VAN-02 сломалась","base_plan_id":1}
Ответ:
{
  "status":"ready",
  "action":{"type":"exclude_vehicles","vehicle_ids":["VAN-02"]},
  "explanation":"Предлагаю пересчитать план без VAN-02.",
  "question":null
}
Если машина не определена: status="needs_clarification", action=null,
question="Укажите ID машины из списка". Если действие не поддерживается:
status="unsupported", action=null и понятное объяснение.
Интерпретация ничего не сохраняет. UI показывает действие, затем по кнопке
«Применить и пересчитать» вызывает /replans. Двойной клик блокируется.
При недоступности AI — 503 с detail; ручное исключение машины остаётся доступным.
Нельзя выдавать заглушку или фиксированный ответ за вызов модели.

AI-модуль Нетесова экспортирует router из backend/app/agent/router.py.
Максим подключает router в create_app и передаёт через согласованную зависимость
контекст текущего плана и доступных ID; модуль не создаёт собственную БД.
Нетесов сначала принимает подготовленный контекст в сервисной функции:
interpret(message, context) -> валидированный результат.
Точный способ внедрения зависимости Максим и Нетесов фиксируют до интеграции.

6. ПРИОРИТЕТЫ
P0: воспроизводимый запуск, импорт, базовый план, исключение машины, новый план,
сравнение, сообщения об ошибках, одна осмысленная AI-команда, честное демо.
P1: объяснение нового плана моделью на фактах, улучшение распределения,
более удобная карта, дополнительный сценарий.
Только если требует кейс: дорожный routing, временные окна, документы, прогнозы.
Не начинать до готовности P0: GPS, роли пользователей, платежи, несколько компаний,
мобильное приложение, инфраструктура очередей, несколько AI-агентов.
