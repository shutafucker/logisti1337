# Критерии тренировочного демо

## Проблема и пользователь

Диспетчер должен быстро оценить последствия недоступности машины: какие заказы
останутся без назначения и можно ли выполнить доставку оставшимся автопарком.
Пользователь — диспетчер последней мили, а не водитель и не модель машинного
обучения.

## P0-сценарий

1. Диспетчер импортирует синтетические заказы и машины Астаны.
2. Система строит исходный план с соблюдением вместимости.
3. Диспетчер сообщает: «VAN-02 сломалась».
4. AI возвращает только проверяемое действие `exclude_vehicles` с ID из
   текущего плана; оно не выполняет расчёт и не меняет данные.
5. Пользователь подтверждает действие, а основной backend вызывает `/replans`.
6. Интерфейс показывает исходный и новый планы, метрики и неназначенные заказы.

## Приёмка

- AI возвращает `ready` только для существующих ID машин и только для
  `exclude_vehicles`.
- Неоднозначная машина возвращает `needs_clarification`; другой тип запроса —
  `unsupported`; ошибка ключа, таймаут и ошибка провайдера дают безопасный 503.
- Расчёт расстояния, ETA, вместимости и назначений выполняет проверенный код
  маршрутизации, не модель.
- Основной набор содержит 12 заказов и 4 машины. `demand` и `capacity` — целые
  **места для посылок**; это не килограммы и не объём.
- `orders.csv` имеет суммарный спрос 17 мест: после исключения `VAN-02`
  остаётся 20 мест вместимости. `orders-capacity-short.csv` имеет спрос 25
  мест: после исключения `VAN-02` часть заказов неизбежно останется
  неназначенной.
- `orders-invalid.csv` содержит одну валидную и одну заведомо неверную строку
  для показа построчной валидации импорта.

## Ограничения

Координаты и ID синтетические; тренировочный город — Астана, но это не
предположение о городе реального кейса. Нет дорожного трафика, live GPS,
оптимальности VRP, учёта уже выполненных доставок или прогноза спроса.
После выдачи реального задания команда заменяет этот документ его фактами и
отбрасывает всё, что не подтверждает критерии жюри.
